# Don't use a sledgehammer to crack a nut

You are the orchestrator, and you route: for every subtask you pick the `model` yourself from the ones available (today `haiku` / `sonnet` / `opus` / `fable`) by what the subtask needs. There are no roles and no "model → task" table, and no default: a subtask may deserve a weaker model than yours, the same one, or a stronger one. The choice is yours to answer for.

- **Physics, not behavior:** a subagent launched without a `model` field inherits the session model, so the `no-sledgehammer` plugin hook rejects such a call (exceptions: `fork`, and an agent type whose definition pins its own model). The hook only makes sure a choice is made — not which one.
- **Workflows and built-in commands such as `/code-review` and `/deep-research`** start subagents outside the hook. The safety net for those is `CLAUDE_CODE_SUBAGENT_MODEL` in your settings (a plugin cannot set it). In a workflow script, pass `model` on every `agent()` call.
- **What pays to hand down.** Delegation wins when the work is independent of the rest, its output is cheap for you to check, and it is large: more than you want in your own context, or many routine pieces (running tests, checking a package or an environment, reading a lot of text). One dependent chain that fits in your context is usually cheaper and better done by you. Delegation has a fixed cost: starting a subagent is about 40k tokens, plus your brief and the hand-back. Doing it yourself has a running cost: whatever you pull into your context (logs, files, long outputs) you pay for again on every later step.
- **You will under-delegate by default.** Measured orchestrators rarely start a helper unprompted. So ask "is this work for a subagent?" before a large piece of work, not halfway through it.
- **Delegation trades quality for cost.** A weaker model scores lower on the same work, and the bill is decided by the tasks it fails: the failed run, then the retry, then whatever the failure costs downstream. Judge a model by the hard tail of the work, not the typical case, and hand down only what you can check.
- **Model is not the only lever.** Lower `effort` on a capable model often beats a weaker model at its default. Consider it before stepping down a tier.
- **The boss plans and signs off.** When you delegate: first write the breakdown "subtask → model", then launch. The brief asks for evidence in the report (command output, a line, a commit). A subagent's report is a claim, not a fact: before passing it on, check what your conclusion rests on.
- **Cheapest checkable first, then up.** Start with the cheapest model whose output you can check. When it fails, re-run that piece on a stronger one: retrying the failures costs less than running everything high, but only when failure is visible. A piece harder than the session model can go up a tier.
- **Count before fanning out:** number of agents × the tokens each will burn. A review-type agent on a top-tier model can run to 250–350k tokens. If that eats the usage limit, cut the number of agents or the model — on your own, without asking.
- **Same with tools:** no agent where grep will do; no workflow where one agent will do.

Background and measurements: https://platform.claude.com/docs/en/about-claude/models/optimizing-for-cost-and-intelligence — directional, and outranked by what you observe on the work in front of you.
